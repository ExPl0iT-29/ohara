# Design

## Context

The app is an Expo managed project with continuous native generation: `/android` and `/ios` are gitignored and regenerated by `expo run:android` or prebuild, so the manifest, permissions and target SDK all come from `mobile/app.json` and Expo config plugins. There is no `eas.json`. Builds today are local debug or release APKs. `android.package` is `com.explooit.mobile`. iOS is disabled for the share intent. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- A first Play upload that cannot embarrass or trap the project: permanent ID, correct artifact, accurate disclosure.
- Everything configurable from repo-tracked files, with secrets kept out.
- Keep the privacy story trivially true by not adding any off-device data flow.

**Non-Goals:**
- Marketing copy and ASO (in `docs/launch`).
- Any monetisation, analytics or crash reporting.

## Decisions

### D1. Application ID `com.ember.ohara`, set in `app.json` only
Change `expo.android.package` and rely on prebuild to propagate it. The `ohara` scheme stays, so share-intent and deep links are unaffected. *Consequence:* Android treats the new ID as a different app with its own SQLite file, so the private build's library does not appear in it.

### D2. Migrate the private library with the existing export and import
No special migration code. The developer exports from the old app and imports into the new one (`local-backup` already round-trips every field, including legacy summary/topics). *Alternative:* a cross-app content provider or shared user ID; rejected as complex, risky, and used once by one person.

### D3. EAS Build for the production app bundle, local build as fallback
Add `mobile/eas.json` with a `production` profile that outputs an `app-bundle`. EAS manages the upload keystore; download and back up the credentials after the first build. *Why:* it avoids hand-managing a keystore and Gradle signing config in a repo whose native folders are generated. *Alternative:* local prebuild plus `./gradlew bundleRelease` with a manually created keystore, kept as a documented fallback. The app itself still has no cloud dependency; this is build tooling only.

### D4. Play App Signing, upload key separate
Enrol in Play App Signing so Google holds the app signing key and the upload key can be reset if lost. Never commit keystores (the `.gitignore` already excludes `*.jks`, `*.key`).

### D5. Version code from `app.json`, bumped per upload
Set `android.versionCode` explicitly and increment it for every Play upload; `version` is the human-readable name. EAS `autoIncrement` may be enabled once the first upload sets the baseline.

### D6. Target SDK pinned through a config plugin
Per Google's Play requirement, new apps and updates must target at least API 36 as of 31 Aug 2026 (verify the current figure on the day of upload). Set `targetSdkVersion` via `expo-build-properties` if the Expo SDK default is lower, and verify in the built manifest rather than trusting the default.

### D7. Permission audit from the merged manifest
After prebuild, list permissions from the merged manifest and remove extras with config. Expected set: `INTERNET` plus whatever `expo-share-intent` and `expo-sharing` require. Anything storage-wide, location, camera or microphone is a bug.

### D8. Privacy policy is a static page on a stable HTTPS URL
A single static HTML file under `docs/privacy/`, served by GitHub Pages from the `docs` folder (the repo is public) until a custom domain exists, then moved to the landing site. The URL goes into the Play listing, the Data safety form and Settings. Writing it as plain language keeps it honest: the app has no backend, so it can say "no data is collected" truthfully.

### D9. Settings opens the policy with the system browser
Use the existing `expo-linking`; no in-app web view and no new dependency. The browser shows its own offline page; the app only handles a failed open with a calm message.

### D10. Data safety answers are derived, not invented
Answers follow from `local-only-operation`: no data collected, no data shared, no account, and the policy link supplied. Disclosure is kept consistent by a spec requirement that any future off-device data flow must update the policy and form first.

### D11. Store-listing deliverables are tracked here, written in the launch plan
Play requires an icon (512x512), feature graphic (1024x500), at least two phone screenshots, short and full descriptions, a category, a content-rating questionnaire, and ads and target-audience declarations. This change tracks that they exist; `docs/launch` owns the wording.

## Risks / Trade-offs

- **Application ID is permanent** → the choice `com.ember.ohara` was made by the owner; the proposal restates it so it is not changed by accident after upload.
- **`com.ember` implies an `ember` domain or brand the owner may not control** → Play does not verify it; the privacy policy and landing page should still live on a domain the owner does own.
- **Personal Play account must run a closed test (reported as 12 testers for 14 days) before production access** → plan it in `docs/launch`; confirm the current rule on Google's Play Console Help before relying on third-party reports.
- **Lost upload key** → Play App Signing allows a reset; credentials are backed up after the first EAS build.
- **EAS free-tier build limits** → fall back to the documented local bundle build.
- **Target SDK bump can break a library** → build and smoke-test the release bundle on a device at the pinned target level before upload.
- **Policy drifts from reality later** → spec requirement D10 plus a checklist item on every future change.

## Migration Plan

1. After `remove-ai-enrichment` lands, change the ID and build a signed bundle.
2. Install the release build from an internal test track on the developer's phone; export from the old app, import into the new one, verify the library, uninstall the old app.
3. Publish the policy page and complete the Data safety and content-rating forms.
4. Hand off to the launch plan's internal, closed and production sequence.
5. Rollback before first upload: revert `app.json`. After upload the ID cannot be undone, so confirm it on the Play Console app-creation screen before pressing create.

## Open Questions

- Custom domain and a dedicated public contact address: the policy currently points contact to GitHub issues and the Play listing address, and the in-app link uses the GitHub Pages URL. Moving to a custom domain later means one constant (`mobile/src/constants/links.ts`) and one redirect, with no spec change.
